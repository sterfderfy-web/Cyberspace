# Первый прототип Cyberspace

Статус: границы первого локального прототипа согласованы владельцем заданием на реализацию. Дата: 1 ноября 2026. Результаты реализации и границы фактических проверок — в [VALIDATION.md](VALIDATION.md).
Основание: [манифест](../MANIFESTO.md) и [инструкции разработки](../AGENTS.md).
Архитектурная основа из PR №2 и уточнения реализации описаны в [архитектуре](ARCHITECTURE.md). Этот документ задаёт критерии и не заменяет отчёт о проверках.

## Цель и сценарий

Проверить, что пространство существует отдельно от интерфейса, доступно нескольким участникам, сохраняет объекты и контролирует действия человека и агента по одним правилам.

Владелец запускает сервер локально, открывает пространство «Мастерская» и создаёт заметку. Второй человек подключается с правом чтения и видит её. Владелец выдаёт ему права изменения и выполнения модуля; второй участник редактирует заметку, оба видят результат. Агент по явному запросу вызывает модуль работы с заметками. Владелец отзывает разрешение агента: следующий вызов отклоняется, включая вызов через уже открытую сессию. После перезапуска сервера пространство и заметка остаются.

Два человека — владелец и второй участник. Права второго участника меняются по ходу сценария, третий человек не требуется.

## Границы

| Входит в первый этап | Последующий этап |
|---|---|
| Один независимо запускаемый сервер, одно демонстрационное пространство | Федерация и межсерверный обмен |
| Браузерный интерфейс: список заметок, редактор, права, состояние соединения | 3D, VR/AR/MR, аватары и голос |
| Два человека и отдельный Actor типа agent | Публичная регистрация и внешние системы идентификации |
| Создание и изменение текстовых заметок | Файлы, медиапотоки, произвольные типы редакторов |
| Один модуль notes с описанием возможностей | Загрузка стороннего исполняемого кода, магазин модулей |
| REST API, подписка на изменения, восстановление после разрыва | Совместное посимвольное редактирование и offline merge |
| Хранение состояния и журнал значимых действий | Распределённый журнал и полная история версий |
| Независимое локальное представление каждой сессии | Полноценная композиция нескольких пространств |
| Экспорт/импорт данных в новую локальную копию | Универсальная межреализационная миграция |

Один сервер — граница эксперимента, а не глобальный центр Cyberspace. Локальная работа означает работу с локальным сервером без интернета, а не редактирование при недоступном сервере.

## Поведение

- **Пространство:** постоянный идентификатор, имя и ревизия. Закрытие всех клиентов не удаляет его.
- **Заметка:** идентификатор, тип, заголовок, текст и ревизия. Пользователь явно сохраняет изменения; при конфликте чужая версия не затирается автоматически.
- **Сессия:** относится к одному Actor. Выбранная заметка и раскладка индивидуальны, не входят в общее состояние.
- **Права:** read, write, execute и manage разграничены. По умолчанию доступ запрещён. Проверки выполняет сервер, в том числе для модуля и подписки.
- **Модуль:** notes декларирует действия create_note и update_note, входные схемы и необходимые права. Человек и агент вызывают эти действия через одинаковый API.
- **Агент:** обязательна воспроизводимая программа без LLM, действующая по явному заданию. Она подтверждает модель участника и API, но не демонстрирует интеллект. Адаптер локальной или удалённой LLM — дополнительный этап, не условие приёмки ядра.
- **Синхронизация:** клиент видит подтверждённое сервером состояние; при разрыве явно показывает недоступность и после подключения получает актуальный снимок.
- **Журнал:** для значимых действий сохраняются Actor, Session, request_id, время, действие, цель и результат. Секреты и полный текст заметки в журнал не попадают.
- **Переносимость:** владелец экспортирует данные пространства; импорт создаёт новую независимую копию под текущим владельцем, без переноса токенов, сессий и чужих полномочий.

## Приёмочные проверки

Статус каждого пункта и пределы проверки приведены в [отчёте](VALIDATION.md); критерии ниже сохранены из PR №2.

| ID | Проверка | Ожидаемый результат |
|---|---|---|
| A01 | Открыть пространство в двух браузерных сессиях | Оба участника видят одну сохранённую заметку |
| A02 | Создать и изменить заметку | Подтверждённое изменение появляется у второго подключённого клиента не позднее 2 секунд в локальной сети |
| A03 | Сменить выбранную заметку в первом окне | Выбор во втором не меняется |
| A04 | Отправить запись напрямую через API от читателя | 403; состояние и ревизия неизменны |
| A05 | Выдать write + execute, затем отозвать write | Запись разрешена после выдачи; после подтверждённого отзыва новые записи отклоняются и в существующей сессии |
| A06 | Выполнить действие агентом, затем отозвать execute | Первый вызов успешен, следующий получает 403; результаты отражены в журнале |
| A07 | Отозвать read при открытой подписке | Сервер прекращает выдачу данных пространства; повторное чтение запрещено |
| A08 | Два редактора сохраняют одну ревизию | Один успех, второй 409; чужой текст не теряется молча |
| A09 | Повторить один request_id с тем же содержимым | Одно изменение и один результат; тот же ID с другим содержимым отклоняется |
| A10 | Перезапустить сервер | Сохранены пространство, заметки, права, ревизии и журнал; клиенты восстанавливают состояние |
| A11 | Разорвать соединение, изменить данные другим клиентом, подключиться заново | Клиент получает актуальный снимок без пропущенного изменения |
| A12 | Отключить интернет при доступной локальной сети | Сервер, браузер и демонстрационный агент продолжают работать без внешних сервисов |
| A13 | Экспортировать и импортировать в чистый экземпляр | Содержимое заметок совпадает; идентичность копии новая, исходные токены и права не действуют |
| A14 | Запрос без аутентификации, поддельный Actor, неверный Origin, некорректный payload | Отказ без изменения данных; Actor определяется серверной сессией |

Условия A02: два клиента, 10 заметок, одна запись в секунду, исправное локальное соединение. Это цель приёмки, не обещанная производительность интернета.

## Порядок реализации и совместная работа

1. Согласовать ТЗ, предложение стека и контракт API в этом PR.
2. Зафиксировать схемы запросов, ответов и ошибок; настроить сборку и минимальный CI.
3. Сделать сквозной путь: сессия → чтение пространства → создание заметки → хранение.
4. Добавить права, отзыв, ревизии, журнал и повторы запросов.
5. Подключить браузер и подписки, проверить восстановление соединения.
6. Добавить демонстрационного агента, экспорт/импорт и выполнить таблицу приёмки.

Разделение для двух разработчиков: первый — ядро, сервер, хранилище и права; второй — браузер и сценарии взаимодействия после согласования контракта. Общие контракты меняются отдельным PR до зависимых изменений. Агент и приёмочные проверки могут выполняться следующим небольшим набором задач.

Прототип готов, когда обязательные проверки A01–A14 выполнены, инструкция запуска воспроизводима на чистом окружении и ограничения записаны в README. Команды запуска и ручной приёмки находятся в [RUNBOOK.md](RUNBOOK.md). Физические телефон и планшет проверяет владелец; эмуляция их не заменяет.
Для локальной разработки, разрешено использовать локальную сеть с последующим размещением на хостинге для проверки во внешней сети.
