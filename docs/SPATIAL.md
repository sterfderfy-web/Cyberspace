# Spatial Foundation — экспериментальный контракт v0

Реализация развивает Core PR1–PR3. SQLite, сессии, права, транзакции, аудит и события сохранены. Three.js 0.187.0 используется только в Web-адаптере. Это локальный пространственный прототип, не стабильный стандарт совместимости и не реализация CAD, SDR, XR или федерации.

## Разделение состояния

| Уровень | Содержимое | Сохранение |
|---|---|---|
| Object | Тип, версия схемы, исходные свойства, собственная ревизия | Существующая таблица objects |
| Shared View | Ссылка на Object, renderer/config, Transform, parent, видимость, прозрачность, слой/порядок, собственная ревизия | Новая таблица views |
| Scene | Все общие View одного Space, ревизия размещения | Таблица scenes |
| PersonalComposition | Подключённые Space, скрытые у пользователя View, личный сдвиг каждого источника | sessionStorage вкладки, по Actor и основной области |
| ObserverState | Камера, цель навигации, выбранный View | sessionStorage вкладки; выделение при новом открытии выбирается заново |
| EditorDraft | Исходная ревизия, изменённый текст, статус и неизвестная команда сохранения Object | Память открытого Workspace; общий для View одного Object |
| Comparison | Пара View, совмещение, alpha, выбор A/B, производные различия | Личная память Workspace; не записывается в Scene/View/Object |

Объект может не иметь View или иметь несколько View с разными визуализаторами и Transform. Изменение или удаление View не меняет Object. Изменение текста обновляет все его представления после получения нового снимка. Shared View всегда принадлежит тому же Space, что и исходный объект и родитель: внешние ссылки не обходят ACL.

Композиция обратима: подключение/скрытие/личный сдвиг источника ничего не записывают в его SQLite. Источники читаются и подписываются раздельно. Их права не объединяются; запись идёт в исходный Space с его текущими правами. Сейчас подключаются только доступные пространства одного экземпляра. Удалённые узлы требуют отдельного протокола доверия.

## Transform и иерархия

Правая система координат: X вправо, Y вверх, Z к наблюдателю в исходном фронтальном виде. Единица position и размеров геометрии View — метр. Scale безразмерный. Rotation — единичный quaternion `{x,y,z,w}`. Локальная матрица `T × R × S`, мировая — `parentWorld × local`; column-major, векторы-столбцы. Личный сдвиг источника применяется клиентом после общей иерархии.

Панель имеет `config.width_m/height_m`. Эти размеры относятся к конкретному представлению, а не к документу. При добавлении панель занимает долю текущего поля зрения камеры; пользователь может изменить её размеры и масштаб. Документ не получает заранее назначенного физического размера или привязки к A4.

Runtime (`packages/spatial-runtime`) содержит только математику и проверки: без Three.js, React, HTTP и SQLite. Запрещены NaN/Infinity, нулевые/отрицательные масштабы, отсутствующие родители, циклы и межпространственные родители. Quaternion с погрешностью нормы до 0.001 нормализуется. Изменение родителя сохраняет локальный Transform; сохранение мировой позиции при переподчинении пока не выполняется автоматически. Удаление родителя с дочерними View возвращает конфликт; сначала измените их родителей.

Лимиты v0: до 256 View на сцену, глубина до 32, position ±1 000 000 м, scale 0.001–1000, размеры панелей 0.001–10 000 м, opacity 0–1, layer −1000–1000, order −10000–10000. Это ограничения числовой модели прототипа, не обещание бесконечной точности или производительности. Видимость наследуется через AND, прозрачность перемножается. Layer/order задают приоритет наложения; выбор совпадающих плоскостей учитывает тот же порядок.

## API и согласованность

Все новые маршруты требуют действующую сессию и read на соответствующий Space:

- `GET /api/v0/spaces/:id/scene`: `{version:0,space,scene_revision,cursor,objects,views,permissions}`.
- `GET /api/v0/spaces/:id/renderers`: дескрипторы зарегистрированных визуализаторов.
- Существующий `GET .../modules` теперь описывает notes, spatial и явно подключённые модули, включая JSON Schema команды.
- Существующий `POST .../actions`: модуль `spatial`, действия `create_view`, `update_view`, `delete_view`; нужны read + write + execute.

Пример создания (UUID источника и request_id заменяются действительными):

```json
{
  "request_id": "00000000-0000-4000-8000-000000000001",
  "module": "spatial",
  "action": "create_view",
  "input": {
    "object_id": "00000000-0000-4000-8000-000000000002",
    "parent_view_id": null,
    "renderer_id": "notes.panel", "renderer_version": 0,
    "config": {"width_m": 2.8, "height_m": 1.75},
    "transform": {
      "position": {"x": 0, "y": 0, "z": 0},
      "rotation": {"x": 0, "y": 0, "z": 0, "w": 1},
      "scale": {"x": 1, "y": 1, "z": 1}
    },
    "visible": true, "opacity": 1, "layer": 0, "order": 0
  }
}
```

Update передаёт полный input, `view_id` и `expected_revision`; delete — только идентификатор/ревизию без input. Источник View неизменяем: для другого Object создаётся новый View. Успех возвращает `view` либо `deleted_view_id`, `scene_revision`, общий `space_revision` и request_id. Проверки, запись, увеличение ревизий, событие, успешный аудит и результат дедупликации выполняются в одной транзакции. Устаревшая ревизия — 409; чужие/недоступные ссылки — 404. Повтор проверяет актуальные права до выдачи ранее сохранённого результата.

События остаются прежними уведомлениями с cursor без содержимого. Пространственный клиент перечитывает сцену и отбрасывает устаревшие ответы. Смена текста двигает общий cursor, но не ревизию размещения. Несколько различных View редактируются независимо через CAS каждого View.

Во время перетаскивания меняется только графическая копия. Один запрос отправляется на pointerup; pointercancel отменяет жест. При новом подтверждённом снимке незавершённый жест отменяется. Числовые поля сохраняются явной кнопкой. Кадры и движения камеры не пишутся в БД. Конфликт сохраняет черновик; кнопка его отбрасывания загружает актуальный View. Неизвестный результат сохраняет исходную команду/request_id в sessionStorage и предлагает безопасный повтор в пределах действующего окна дедупликации (24 часа).

## Модули, визуализаторы и возможности

`ModuleDefinition` содержит id/version, dependencies, request_schema, действия с required_permissions и execute. Реестр проверяет уникальность и наличие зависимостей. Core выполняет авторизацию, транзакцию, дедупликацию и аудит; обработчик получает контекст, ограниченный текущим Space. Новый тип объекта добавляется через модуль, без ветвления по типам в Core. Legacy snapshot/export фильтруют поддерживаемые заметки, полный scene содержит универсальные Object.

`RendererDescriptor` содержит id/version, поддерживаемые object_types, required_capabilities, config_schema. Сервер проверяет конфигурацию и соответствие типа. Список Capability уже допускает 2D, 3D, stereo, 3DoF, 6DoF, hand tracking, passthrough, spatial anchors; наличие имени не означает реализацию устройства или полномочие управления им.

Связывание доверенных модулей/дескрипторов выполняется в apps/server; дополнительные определения можно передать через `extraModules`/`extraRenderers`. Web имеет отдельный `VisualizerRegistry` и зарегистрированные `notes.panel` (документ) / `notes.summary` (сводка). Адаптер получает копии снимков и создаёт геометрию. Его интерфейс исполнения относится к Web/Three.js, а универсальные контракты не зависят от этого интерфейса. Другой клиент может использовать свой движок.

Неизвестный этому клиенту визуализатор остаётся в списке View с идентификатором и параметрами; графическая геометрия для него пропускается. Реестр не загружает код из сети, пользовательских URL или БД. Здесь нет песочницы: разрешены только проверенные встроенные расширения. Визуализатору не передаются токены и контекст серверных команд; контракт не даёт права или канала управления устройством. Произвольный недоверенный плагин требует будущей изоляции.

## Миграция SQLite v1 → v2

Перед изменениями существующей v1 создаётся согласованная резервная копия `*.before-v2-<UUID>.sqlite` через VACUUM INTO, учитывающий WAL. Копия открывается read-only и проверяется quick_check. Затем одна транзакция создаёт scenes/views, индексы, составные внешние ключи и запись миграции 2. Существующие объекты, права, сессии, ревизии, requests и audit сохраняются без изменения. Старым объектам View автоматически не назначаются. Повторный запуск не повторяет миграцию и резервное копирование; схема новее v2 останавливает запуск.

При сбое транзакция откатывается. Для возврата к PR3 остановите все процессы сервера, сохраните текущую БД вместе с WAL/SHM и восстановите v1 из созданной копии в отдельном каталоге с прежними credentials. Не запускайте старый сервер поверх рабочей v2 и не подменяйте файл при открытых соединениях. Копии содержат те же чувствительные данные, что и БД, и остаются вне git.

JSON export/import v0 по-прежнему переносит **заметки**, не View. Для полного сохранения текущего экземпляра используется резервная копия SQLite. Версионированный перенос сцен/ресурсов — следующий отдельный этап, а не молчаливое изменение формата v0.

## PR6: интерактивные документы и сравнение

`notes.panel` теперь предоставляет нативные input/textarea непосредственно в сцене. DOM-панель использует перспективную матрицу камеры, `parentWorld × local`, размеры View и личный сдвиг источника. CSS-пиксели редактора (базовая ширина 640) — разрешение клиентского интерфейса, а не физический размер документа. Поворот, перспектива, масштаб и иерархия проверяются сопоставлением углов панели с WebGL; браузерный тест нажимает на редактор повёрнутого View без принудительного обхода hit testing. `notes.summary` остаётся компактным превью.

Режимы выбираются над сценой: перемещение View, масштаб View горизонтальным жестом, редактирование, панорамирование и орбита. В редакторе работают выделение, прокрутка, клавиатура и копирование/вставка браузера. Сохранение явно кнопкой или Ctrl/Cmd+S. Жесты размещения не выделяют текст; ввод не запускает drag. Прозрачность, слой и порядок меняются в инспекторе с явным сохранением. Для масштаба, как и перемещения, отправляется одна команда на завершение жеста.

Черновик отделён от снимка Object и имеет исходную ревизию. Все View того же Object в этой рабочей области показывают общий черновик. Чужое обновление не затирает его; CAS-конфликт требует явного перечитывания. При потерянном ответе повтор использует ту же команду/request_id и блокирует дальнейшее изменение её тела. Неизвестная команда документа хранится только до закрытия Workspace/перезагрузки; это отличается от существующего восстановления команды View из sessionStorage. Сохранённые документы и общие View восстанавливаются с сервера.

Отметьте два View в списке и включите сравнение. Совмещение и размер второй панели вычисляются в личном графическом состоянии; кнопки A/B, прозрачность верхней панели и выход не пишут в SQLite. Редактирование Transform сравниваемой пары временно заблокировано, текст редактировать можно. Выход возвращает актуальные общие Transform, включая полученные за это время изменения других участников. Остальные участники не получают чужую композицию сравнения.

Текстовый инструмент под сценой показывает добавленные/удалённые строки и изменённые Unicode-фрагменты, синхронизирует вертикальную/горизонтальную прокрутку. Локальный черновик явно отмечен. Пересчёт запускается после 150 мс без ввода, в Worker; старое задание прекращается при смене данных/закрытии. Ограничения: 64 КиБ UTF-8 на документ, 4000 строк результата, 250 мс для строкового diff, 20 мс для пары изменённых строк, общий предел Worker 1 секунда. Превышение показывает сообщение, а не блокирует интерфейс. Автоматического merge нет.

Отдельная кнопка открывает сравнение двух синтетических локальных изображений 320×200: Alpha Blend, Difference (абсолютная разность RGB), прозрачность, общий zoom/pan и сброс. Исходные пиксели не меняются. Это демонстрация клиентского инструмента, не новый тип Object и не загрузка файлов.

Адаптер сохраняет визуализатор по View ID и renderer id/version. `update` обновляет CanvasTexture только при новой ревизии Object; изменение размеров заменяет только геометрию. Удаление/смена визуализатора вызывает `dispose`, закрытие сцены освобождает материалы, текстуры, геометрию, RAF и обработчики. DOM keyed по View ID сохраняет редактор, фокус и позицию курсора при снимках сцены. Новый Web-визуализатор регистрирует `create/update/dispose`; `interactive` включает клиентскую панель для поддерживаемого типа. Новый тип редактора добавляется в Web-слой, без ветвлений Core. Серверный дескриптор и модуль по-прежнему регистрируются независимо.

## Ограничения и продолжение

DOM/WebGL-композиция экспериментальная: DOM-панели сортируются по слою/порядку и расстоянию до центра; попиксельной окклюзии пересекающихся панелей и WebGL-геометрии нет. Панель, пересекающая плоскость камеры, скрывается целиком. Автоматический LOD и манипулятор вращения отсутствуют; quaternion задаётся численно. Графика требует WebGL2; при отказе остаются список и параметры сохранённых View и прежний раздел «Заметки». Черновики и сравнение не переживают закрытие Workspace; камера/композиция и неизвестная команда View хранятся в sessionStorage. Между устройствами личная композиция не переносится. Проверки реальных сенсорных устройств ещё нет; измерения восьми документов и их границы приведены в [VALIDATION.md](VALIDATION.md).

В следующем этапе можно добавить модуль объектов и его визуализаторы, версионированный перенос сцен, удобные манипуляторы и отдельные клиентские адаптеры. Потоки SDR, CAD-геометрия, XR и межсерверное доверие потребуют своих модулей/протоколов и проверок; они не реализованы этим фундаментом. Цели и критерии R1–R7 сохранены в [ROADMAP](ROADMAP.md).
